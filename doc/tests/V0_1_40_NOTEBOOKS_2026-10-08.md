## Lot 1 — Références et cycle d'exécution

Attendu : une référence utilise uniquement un résultat réussi dans le contexte
courant. Modifier sa source ou ses variables invalide ses dépendants transitifs.
Une annulation, fermeture ou modification de contexte neutralise les réponses
pendantes ; un lot en erreur n'annonce jamais un succès global.

Les 15 premiers scénarios Chromium échouaient avant correction, après résolution
d'une erreur d'initialisation React propre à la fixture. Les défauts reproduits :

- « Tout exécuter » envoyait les références non résolues, faute de résultat publié
  avant le rendu suivant.
- Modification de source, valeur, définition ou suppression de variable et
  suppression de cellule conservaient des dépendants marqués réussis.
- Annulation, édition, effacement, changement de session, namespace ou workspace
  acceptaient une réponse tardive.
- Un lot échoué annonçait « Toutes les cellules exécutées » ; deux appels immédiats
  pouvaient envoyer deux requêtes ; fermer le notebook ne demandait pas l'annulation.

Le hook publie maintenant son état synchrone avant de poursuivre un lot.
L'invalidation suit les labels jusqu'aux dépendants, y compris les cycles.
Les références absentes, périmées, masquées, tronquées ou ambiguës sont refusées avant tout IPC avec
un message traduit dans les neuf locales. Une erreur source bloque aussi ses
dépendants lorsque la poursuite après erreur est demandée. Un test pur supplémentaire a reproduit l'acceptation de valeurs masquées comme
cible de mutation. Le hook conserve maintenant aussi la troncature annoncée par
le transport ; deux parcours Chromium vérifient qu'aucune mutation dépendante
n'est envoyée depuis une colonne masquée ou un résultat tronqué. Les valeurs
insérées restent hors du rescannage corrigé le 6 octobre.

Chaque exécution possède une identité ; réponses et finalisations anciennes ne
peuvent pas remplacer un nouvel état. L'annulation vise la session d'origine.
Les changements de contexte retirent les résultats et l'historique d'annulation ;
undo/redo ne restaurent pas des lignes d'un ancien contexte. Les graphiques
n'utilisent plus une source périmée ou un label ambigu. Annuler côté frontend
n'est pas une preuve de rollback d'une mutation déjà reçue par le moteur.

Validation du lot : 18 scénarios du hook réel dans Chromium passent avec IPC
simulé, dont reprise d'une chaîne invalide, undo/redo et poursuite après erreur.
Les tests purs vérifient également états non réussis, colonnes/labels ambigus,
cycles et préservation des réglages d'affichage. Les contrôles finaux du rapport
précisent les commandes et la mesure de poids commune aux lots.

Les contrôles backend de licence, masquage, lecture seule, Sandbox et confirmation
production ne sont pas modifiés. Cette fixture ne les qualifie pas et n'ouvre
aucune base réelle. Les parcours natifs Tauri restent non exécutés.

## Lot 2 — Sauvegarde, import et réouverture

Attendu : les changements faits pendant une sauvegarde restent à sauvegarder ;
l'import protège le document courant ; un fichier ouvert remplace également les
références internes, le focus et l'historique, sans réutiliser ses anciens résultats.

Cinq des six premiers scénarios de fichiers du hook reproduisaient un défaut :
statut propre malgré une édition pendant l'écriture, ancienne requête exécutée
après réouverture, import sans confirmation, import sans brouillon immédiatement
récupérable et édition perdue pendant la lecture. Le cas annulation/erreur disque
passait déjà. Les opérations de sauvegarde/ouverture/import sont maintenant
sérialisées ; leur réponse est rattachée au contexte et à la révision capturée.
Une lecture devenue périmée laisse le document courant intact. Une sauvegarde
écrit sa révision initiale et conserve les nouvelles saisies dans le brouillon.

Six des huit premiers tests de fichiers échouaient : quatre structures invalides
acceptées, cellules Mongo transformées en SQL et bloc Markdown non SQL tronqué.
Le lecteur vérifie la structure minimale, les identifiants uniques et les variables.
L'export/import Markdown conserve le type SQL/Mongo et protège les fences imbriquées.
Cinq autres tests ont reproduit un découpage SQL incorrect dans commentaires,
dollar-quotes, identifiants cités et trigger. Les scripts complexes restent dans
une seule cellule ; leur découpage est confié au moteur, sans nouveau parseur SQL.
Les scripts simples restent divisés en cellules et préservent les points-virgules
entre guillemets.

Les nouveaux brouillons conservent les sources et valeurs courantes des variables,
sans persister les lignes de résultats, qui n'étaient pas réutilisables après
réouverture. Le démontage conserve le brouillon sale. Les anciens brouillons
ne sont pas assainis globalement : seuls ceux réécrits utilisent cette politique.
Les résultats enregistrés explicitement dans un fichier restent présents dans
ce fichier ; l'exécution dans une nouvelle session demande une nouvelle lecture.
Un test supplémentaire a reproduit un brouillon restauré marqué à tort comme
propre : il reste maintenant sale et soumis à la confirmation de remplacement.
Les expressions de champ Mongo sans label de notebook connu restent inchangées.

Les 16 tests IO/import/export utilisent des fichiers temporaires réels pour QNB
et HTML, via les adaptateurs Node remplaçant les plugins Tauri. Ils relisent le JSON,
les valeurs exactes et le HTML échappé. L'export Markdown reste un format de partage
SQL/Mongo/texte, pas une sauvegarde exhaustive des cellules IA/contrat/chart : QNB
reste le format de sauvegarde. Les validations de permissions natives et du profil
complet v0.1.39 restent non exécutées.

## Chargement et poids

Le lecteur de notebooks est chargé à l'ouverture depuis le menu et la palette.
La bibliothèque de requêtes utilise un composant différé commun à AppOverlays
et QueryPanel. Après sa première ouverture, elle reste montée pour conserver
recherche et sélection. Chromium vérifie le vrai AppOverlays avec les autres
panneaux simulés : aucun téléchargement du module avant ouverture, chargement
à la demande, fermeture puis recherche conservée à la réouverture.

Le premier essai dépassait le JS initial de 86 octets bruts / 446 gzip. Différer
la bibliothèque sur un seul point d'entrée ne suffisait pas, car QueryPanel
l'importait aussi statiquement. Les deux entrées utilisent maintenant le même
composant différé. Les seuils ne sont pas modifiés.

Référence locale : `.perf/v0-1-40-2026-10-08-before.json`, prise avant les nouveaux
correctifs avec les changements du 6 octobre déjà présents. Candidate :
`.perf/v0-1-40-2026-10-08-notebooks-final.json`. Node 24.21.0, pnpm 11.3.0, Vite 8.1.0,
Linux x86_64 ; empreintes et chaîne identiques entre référence et candidate.
La référence du 6 octobre utilisait Node 26.10.0 : elle n'est pas réutilisée comme
comparaison directe. Cette mesure ne couvre ni RAM/CPU ni latences natives.
