## Lot 1 — Annulation, ciblage workspace et PostgreSQL réel

Critères : une annulation empêche l'envoi des requêtes suivantes, préserve les
résultats déjà obtenus dans un rapport explicitement annulé et ne prétend pas
annuler une mutation déjà envoyée. Une session d'origine inconnue ou appartenant
à un autre workspace est refusée avant toute exécution ou capture. Les deux
cibles A/B sont contrôlées avant la première requête.

Les trois scénarios PostgreSQL historiques passent avant modification. Trois
nouvelles régressions échouent ensuite sur le code précédent : la seconde requête
part malgré l'annulation, l'annulation pendant la dernière requête est invisible,
et une session d'un autre workspace peut exécuter et capturer des résultats.

Le runner vérifie l'annulation aux frontières de dispatch, conserve les résultats
terminés et marque les entrées restantes `skipped/cancelled`. Le champ optionnel
`RunMeta.cancelled`, faux par défaut à la lecture d'un ancien rapport, rend l'état
visible après réouverture. La requête en cours peut finir ; il n'y a ni promesse
d'interruption immédiate du driver ni rollback implicite. Le rapport affiche
cette limite dans les neuf langues. Le compteur A/B utilise les requêtes
terminées, sans compter les événements de progression comme des exécutions.

Le contrôle d'origine est dans le `SessionManager` partagé. Les chemins Replay
et démarrage d'enregistrement le réutilisent. Le jeu et l'identité du workspace
sont lus sous le même verrou pour éviter de ranger les captures d'un projet dans
un autre pendant un changement de workspace.

### Limites

Activation Pro réelle, trousseau, transport Tauri, changements de workspace via
la fenêtre native et autres moteurs ne sont pas qualifiés ici. Les requêtes
Replay utilisent le preflight commun ; le Sandbox de modifications de grille
n'est pas un mode transactionnel global du runner et n'est pas qualifié par ces
tests. Les politiques de masquage modifiées après une capture historique et les
arrêts brutaux du processus pendant l'écriture restent à examiner. Le nouveau
champ est rétrocompatible à la lecture, sans migration des anciens rapports.

## Lot 2 — Réouverture et rétention des rapports

Quatre nouvelles régressions de stockage échouent avant correction : un ancien
A/B masque un rejeu normal plus récent ; un rapport corrompu disparaît comme s'il
n'avait jamais existé ; une rétention de un supprime la référence du diff ; une
rétention de zéro supprime aussi les métadonnées du rejeu courant.

Le lecteur parcourt maintenant les exécutions par date, choisit A/B seulement
à l'intérieur de l'exécution concernée et propage une erreur de lecture. Le hook
vide l'ancien rapport avant chargement et remonte l'erreur ; un quatrième scénario
Chromium reproduit puis vérifie cette correction avec IPC simulé.

La rétention intervient après sauvegarde du rapport. Elle conserve au moins le
dernier rejeu, la référence d'enregistrement et les références directes des
rapports conservés, sans compter l'enregistrement dans le quota. Un A/B peut donc
retenir une exécution supplémentaire. Une référence illisible suspend la purge
pour préserver les captures récupérables. Cela ne modifie aucun droit commercial.

Le test PostgreSQL A/B impose maintenant une rétention de un et recharge les deux
captures après le rejeu ; les neuf scénarios réels passent de nouveau. Deux tests
supplémentaires couvrent la lecture des anciennes métadonnées sans `cancelled` et
l'absence de purge destructive après corruption. Typecheck, Biome ciblé et contrôle
du diff passent. Les écritures interrompues par un arrêt brutal du processus ne
sont pas rendues atomiques par ce lot.

## Lot 3 — Réponses tardives et contexte frontend

Sept scénarios Chromium échouent avant correction : sélection tardive, rapport
stocké tardif, résultat de rejeu tardif après une nouvelle sélection, double
invocation dans le même cycle, changement de connexion, changement de workspace
et erreur devenue obsolète. Un huitième cas reproduit ensuite un ancien rapport
stocké remplaçant le résultat d'un rejeu tout juste terminé.

Le hook rattache les lectures et actions à la sélection et au contexte qui les
ont lancées. Les continuations obsolètes cessent avant de publier un résultat,
de notifier ou d'enchaîner d'autres lectures. Un verrou synchrone empêche les
doubles départs. Le rapport chargé depuis le disque perd sa priorité dès qu'un
nouveau rejeu démarre. L'onglet Replay est remonté sur changement de connexion ou
de workspace pour réinitialiser aussi les options locales de mutation et A/B.
Ce dernier branchement AppLayout est contrôlé par typecheck ; les scénarios de
contexte navigateur montent le hook réel, pas toute la fenêtre native.

Les 17 scénarios de `scripts/test-replay-ui.mjs` passent : trois sur le composant
de rapport, un sur la corruption et treize sur le cycle asynchrone du hook. Ils
incluent A/B, acceptation de référence, colonnes ignorées, suppression et refus
d'une ancienne callback de mutation. L'IPC et les notifications sont simulés.
Typecheck et Biome passent ; les deux avertissements de dépendances AppLayout
étaient déjà présents. La suite TypeScript exécutée pendant cette reprise compte
336 tests dans 39 fichiers ; les scénarios du hook sont dans Chromium, pas Vitest.

Les 71 tests unitaires Replay Pro (65 initiaux et six de stockage) et les 259 tests
Core desktop passent, ainsi que les trois tests ciblés du SessionManager. Un
changement de contexte frontend ne promet pas d'interrompre la requête déjà
dispatchée au backend : ses résultats restent dans son workspace d'origine. Le
statut global de l'enregistreur et ses aperçus lors d'un changement de workspace,
ainsi que l'adoption d'une nouvelle référence sans capture, restent à examiner
séparément. La qualification Tauri et les autres moteurs restent ouvertes.

## Lot 4 — Qualification PostgreSQL complémentaire

L'instance jetable est aussi utilisée pour qualifier les correctifs précédents,
sans les réécrire :


15 tests réussissent, zéro ignoré, 25 autres tests filtrés : cinq tests driver
(parcours CRUD/schema/transaction, pagination keyset, streaming, décimales exactes,
ciblage de clé BIGINT) et dix tests Time Travel/capture. Ces derniers vérifient
les images finales après trigger, les lots commit/rollback, les permissions
INSERT seul et RLS, les erreurs de lecture/SQL, le refus de commit d'une
transaction avortée, la récupération après annulation, le timeout et le savepoint
appelant, les écritures confirmées malgré une image illisible et l'absence de
repli en autocommit après perte de connexion.

Ces 15 tests sont distincts des neuf tests `replay_e2e`. Ils utilisent le vrai
PostgreSQL 16.15 local et les crates du produit ; ils ne passent pas par une
fenêtre Tauri, un profil utilisateur historique ni le packaging. Aucun autre
moteur ne devient qualifié par ce résultat.
