## Attendu et reproduction

Une session API doit recevoir les changements de masque de sa connexion dans
son workspace, sans toucher une connexion de même identifiant dans un autre
workspace. Deux premières requêtes doivent partager la même session. Une
session expirée doit permettre une reconnexion ou une erreur récupérable.

La référence existante passe ses 16 tests de handlers. Après ajout de six tests,
17 passent et cinq échouent avant correction :

| Scénario | Observation avant correction | Nature de la preuve |
| --- | --- | --- |
| Masquage mis à jour après ouverture | La valeur synthétique revient en clair au lieu du masque | Driver SQLite réel, service de masquage réel |
| Même cas via le handler | La réponse JSON contient encore la valeur synthétique | Handler Axum appelé directement, SQLite réel |
| Session expirée dans le cache | Timeout de deux secondes, verrou repris alors qu'il est déjà détenu | Tokio et SessionManager réels, session inexistante |
| Deux ouvertures simultanées | Une ouverture échoue avec `database is locked` | Deux appels concurrents, fichier SQLite temporaire |
| Workspace vide | Une session est publiée malgré l'identité manquante | SessionManager et SQLite réels |
| Connexion indisponible puis reprise | Réussit déjà avant correction | Driver inconnu puis SQLite réel |

Les tests n'utilisent aucune connexion sauvegardée personnelle ni aucun secret
réel. Le chargement de configuration est injecté dans un helper privé pour
éviter le keyring système ; ouverture, cache, identité et masquage exécutent
le même chemin que le handler de production.

## Correctif

Le cache est verrouillé pendant lookup, ouverture et publication. Cela évite
le verrou imbriqué sur session expirée et les ouvertures concurrentes non suivies.
Les ouvertures initiales de connexions différentes sont sérialisées aussi ;
l'exécution SQL est hors de ce verrou. Le coût natif à froid reste à mesurer.

La session reçoit l'identité de workspace capturée au démarrage du serveur,
avant son identité de connexion sauvegardée, son masque initial et sa publication.
Si le rattachement échoue, elle est déconnectée et n'entre pas dans le cache.
Le rafraîchissement existant de `SessionManager::update_connection_masking`
peut ainsi sélectionner les sessions API du bon workspace. Aucune règle de
licence, authentification ou exposition réseau n'est modifiée.

Le test du handler vérifie Bearer absent/invalide, masque mis à jour, entier
`9007199254740993` conservé dans le JSON Rust, limite d'une ligne et indicateur
`truncated`. Un endpoint contenant un DELETE est refusé par le contrôle runtime ;
une lecture SQLite vérifie que la ligne protégée est toujours présente.
Le test ne prouve pas que tous les consommateurs JavaScript lisent un entier
JSON au-delà de 2^53 sans l'arrondir.

## Environnement et limites

Linux x86_64. Les premiers tests utilisent le cache Cargo présent au début de
la reprise. Ce répertoire a disparu pendant la compilation suivante, sans
commande de nettoyage dans cette tâche. La reconstruction utilise ensuite
`/home/raphael/.cache/qoredb-v0-1-40-target`, avec quatre jobs.
Le téléchargement de DuckDB 1.5.3 a produit un chemin de liaison relatif pour ce
répertoire personnalisé ; la bibliothèque copiée sous `debug/deps` est fournie
au linker par `LIBRARY_PATH`. Aucun changement du driver ou de la configuration
Cargo n'est nécessaire au correctif.

Les commandes de qualification sont données ci-dessous avec le chemin local
isolé. Les résultats finaux sont consignés après exécution. Pas de recette
Tauri, keyring réel, activation/expiration de licence, moteur distant ou charge
HTTP simultanée dans ce lot. Le binding workspace des sessions est couvert ;
la totalité des courses pendant arrêt/reconfiguration du serveur ne l'est pas.

```bash
LIBRARY_PATH=/home/raphael/.cache/qoredb-v0-1-40-target/debug/deps cargo test --manifest-path src-tauri/Cargo.toml --target-dir /home/raphael/.cache/qoredb-v0-1-40-target -j 4 -p qoredb --features pro --lib api:: -- --test-threads=1
LIBRARY_PATH=/home/raphael/.cache/qoredb-v0-1-40-target/debug/deps cargo test --manifest-path src-tauri/Cargo.toml --target-dir /home/raphael/.cache/qoredb-v0-1-40-target -j 4 -p qoredb --lib
rustfmt --edition 2024 --check src-tauri/src/api/handlers.rs
pnpm docs:check
git diff --check
```

- Pro, filtre `api::` : 50 tests réussis, zéro ignoré, dont six nouveaux tests
  de cycle et handler. Les tests voisins couvrent également authentification,
  stockage d'endpoints, OpenAPI, rate limit, démarrage/arrêt sur port éphémère,
  génération de certificats et arrêt idempotent via l'adaptateur de commande.
- Core, bibliothèque desktop : 259 tests réussis, zéro ignoré. Ce résultat prouve
  la compatibilité de compilation/tests Core, pas une licence Core activée dans
  un binaire Pro ni une recette native.
- Formatage Rust ciblé, `docs:check` et `git diff --check` : réussis.
- SQLite réel utilisé par les nouveaux tests. Le handler est invoqué directement,
  sans socket HTTP pour ces requêtes. Le keyring et les serveurs distants restent
  non exécutés ; le frontend et les artefacts de packaging ne changent pas dans
  ce lot Rust.
